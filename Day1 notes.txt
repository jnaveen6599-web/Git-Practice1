1. ENVIRONMENTS
----------------------------------------------------------
An "environment" is a place where your code runs, with its own
settings, database and servers.

  Development (dev)  : your laptop. You write and break things freely.
  Testing / QA       : a copy where testers check the app.
  Staging            : a near-exact copy of production, final check.
  Production (prod)  : the real app that real users use.

Why separate them? So a bug you create while coding never hurts
real users or real data.

Environment variables / config: settings that differ per environment
are kept OUT of the code, usually in a .env file:

    DATABASE_URL=postgres://localhost/mydb_dev      (dev)
    DATABASE_URL=postgres://prod-server/mydb        (prod)
    OPENAI_API_KEY=sk-xxxx                          (secret!)

Rule: never commit secrets (.env) to Git. Add .env to .gitignore.


----------------------------------------------------------
2. ENVIRONMENT TESTING
----------------------------------------------------------
Checking that the app works correctly IN a given environment, not
just on your laptop. "It works on my machine" is the classic problem.

What you check:
  - Correct versions installed (Python 3.11, Node 20, etc.)
  - Environment variables are set
  - App can connect to the database / other services
  - Ports open, permissions correct
  - Config points to the right database (test app must NOT touch prod data)

Example: a simple health check endpoint.

    # Python / Flask
    @app.route("/health")
    def health():
        return {"status": "ok", "db": check_db_connection()}

After deploying to the test server you open
http://test-server/health and confirm it says "ok".

Example smoke test (a quick "is it alive?" test) after deployment:
    curl http://test-server/health
    -> {"status":"ok","db":true}

If it fails -> the environment is set up wrong (missing env var,
wrong DB password, firewall closed), not necessarily your code.

3. EC2 (Amazon Elastic Compute Cloud)
----------------------------------------------------------
EC2 = a computer (virtual server) that you rent from Amazon (AWS),
running 24/7 in their data center. You can install your app on it so
the whole internet can reach it.

Key terms:
  - Instance      : one rented virtual server (e.g. type t2.micro).
  - AMI           : the starting image/OS (Ubuntu, Amazon Linux).
  - Key pair      : a .pem file used to log in securely via SSH.
  - Security Group: the firewall (which ports are open: 22 SSH,
                    80 HTTP, 443 HTTPS).
  - Elastic IP    : a fixed public IP address.
  - EBS           : the disk attached to the instance.

Basic steps to host an app on EC2:
  1. AWS Console -> EC2 -> Launch instance (Ubuntu, t2.micro free tier)
  2. Create/download key pair (my-key.pem)
  3. Security group: allow ports 22, 80, 443
  4. Connect:
        ssh -i my-key.pem ubuntu@<public-ip>
  5. Install tools and get your code:
        sudo apt update
        sudo apt install python3-pip git nginx
        git clone https://github.com/you/your-app.git
        cd your-app && pip install -r requirements.txt
  6. Run the app:
        gunicorn app:app --bind 0.0.0.0:8000
  7. Nginx forwards port 80 -> 8000 so users visit http://<public-ip>

Tip: stop/terminate instances you don't use, or AWS will bill you.

4. INTEGRATION AND INTEGRATION TESTING
----------------------------------------------------------
Integration = connecting separate pieces so they work together.
  Examples: frontend <-> backend API, backend <-> database,
            backend <-> payment service, backend <-> LLM API.

Integration testing = testing that those pieces really work TOGETHER
(as opposed to unit testing, which tests one small function alone).

Testing pyramid:
  Unit tests         -> one function         (many, fast)
  Integration tests  -> several parts together (some)
  End-to-end tests   -> whole app like a user  (few, slow)

Example unit test (alone):
    def add_tax(price): return price * 1.18
    assert add_tax(100) == 118

Example integration test (API + database):
    def test_create_user():
        r = client.post("/users", json={"name": "Asha"})     # API call
        assert r.status_code == 201
        user = db.query("SELECT * FROM users WHERE name='Asha'")
        assert user is not None                              # saved in DB

This proves the API route, the validation and the database all work
together. Use a TEST database, not the real one.

Common tools: pytest (Python), Jest/Supertest (JavaScript),
Postman (manually test APIs), Cypress/Playwright (browser tests).

5. FUNCTIONAL FEATURES
----------------------------------------------------------
Functional features = what the app DOES (the behaviors users see).
Non-functional = HOW WELL it does it (speed, security, uptime).

Example, an online shop:
  Functional     : sign up, log in, search products, add to cart,
                   pay, view order history, chat with support bot.
  Non-functional : page loads in <2s, handles 1000 users, data
                   encrypted, works on mobile.

Functional testing = checking each feature behaves as required.
Example test cases for "Login":
  - correct email+password        -> user enters dashboard
  - wrong password                -> error "Invalid credentials"
  - empty fields                  -> validation message
  - 5 wrong attempts              -> account temporarily locked

Tip: write features as user stories:
  "As a user, I want to reset my password so that I can regain access."

6. RAG CHATBOT, ITS DATABASE AND EMBEDDING MODEL
----------------------------------------------------------
Problem: an LLM (ChatGPT, Claude) doesn't know YOUR private data
(company PDFs, FAQs, manuals) and may make things up.

RAG = Retrieval-Augmented Generation. Before the LLM answers, we
RETRIEVE relevant pieces of your documents and give them to the LLM
as context, so it answers from your data.

--- Step A: Indexing (done once, offline) ---
  1. Load documents (PDF, Word, web pages).
  2. Split them into small "chunks" (~300-500 words each).
  3. Convert each chunk into an EMBEDDING (a list of numbers).
  4. Store chunk text + embedding in a VECTOR DATABASE.

--- Step B: Question answering (every user question) ---
  1. User asks: "What is the refund policy?"
  2. Convert the question into an embedding (same model!).
  3. Vector DB finds the chunks whose embeddings are closest
     (most similar in meaning).
  4. Build a prompt:
        "Answer using ONLY this context:
         <top 3-5 chunks>
         Question: What is the refund policy?"
  5. Send to the LLM -> it writes the answer.
  6. Show the answer (optionally with sources).

Diagram:
   Docs -> chunks -> embedding model -> Vector DB
   Question -> embedding model -> search Vector DB -> chunks
        -> LLM (question + chunks) -> Answer

What is an EMBEDDING MODEL?
  A model that turns text into a vector (e.g. 384 or 1536 numbers)
  so that texts with similar MEANING have vectors close together.
  "car" and "automobile" end up near each other; "banana" far away.
  Popular embedding models:
    - OpenAI text-embedding-3-small / -large  (paid API)
    - sentence-transformers all-MiniLM-L6-v2 (free, runs locally)
    - Cohere embed, Google text-embedding, Voyage AI
  Important: use the SAME embedding model for documents and questions.

What is a VECTOR DATABASE?
  A database built to store vectors and quickly find "nearest" ones
  (similarity search, e.g. cosine similarity).
  Options:
    - FAISS        : library, runs locally, great for learning
    - Chroma       : simple, local, beginner friendly
    - Pinecone     : managed cloud service
    - Qdrant, Weaviate, Milvus : open-source/server options
    - pgvector     : vector support inside PostgreSQL
    - AWS OpenSearch / Amazon Bedrock Knowledge Bases (on AWS)
  You often ALSO keep a normal database (PostgreSQL/MongoDB) for
  users, chat history and metadata.

Tiny example (Python, Chroma + sentence-transformers):

    from sentence_transformers import SentenceTransformer
    import chromadb

    model = SentenceTransformer("all-MiniLM-L6-v2")   # embedding model
    db = chromadb.Client().create_collection("docs")  # vector DB

    chunks = ["Refunds are allowed within 30 days.",
              "Shipping takes 3-5 business days."]
    db.add(ids=["1","2"],
           documents=chunks,
           embeddings=model.encode(chunks).tolist())

    q = "How long do I have to return an item?"
    hits = db.query(query_embeddings=model.encode([q]).tolist(),
                    n_results=1)
    context = hits["documents"][0][0]   # "Refunds are allowed within 30 days."
    # Now send context + q to an LLM to write the final answer.

Typical RAG stack: Python + LangChain or LlamaIndex + embedding
model + vector DB + LLM (Claude/GPT) + FastAPI backend + React UI.

7. INCREMENTAL PUSH
----------------------------------------------------------
Incremental push = pushing your work to the remote repo (GitHub) in
SMALL, frequent steps (one feature/fix per commit) instead of one
giant upload at the end.

Why:
  - Easy to review and find which change broke something
  - Easy to undo a small commit
  - Backup of your work, less merge conflict pain
  - Teammates always see current progress

Workflow:
    git checkout -b feature/login        # work on a branch
    # ...edit code...
    git add login.py
    git commit -m "Add login form validation"
    git push origin feature/login        # push small change

    # ...more work...
    git add auth.py
    git commit -m "Add password hashing"
    git push                              # push again (only new commits go)

Git only uploads the NEW commits since the last push, which is
itself "incremental". First push of a new branch needs:
    git push -u origin feature/login

Also, incremental can mean in CI/CD: deploying only what changed
(or incremental indexing in RAG: embedding only new/changed
documents instead of re-processing everything).

Good commit habits: small commits, clear messages, pull before push
(git pull --rebase), never commit secrets.

8. SERVICES NEEDED TO BUILD A WEB APPLICATION
----------------------------------------------------------
A web app is made of several parts. Each part has a job:

 1. FRONTEND (what the user sees)
      HTML, CSS, JavaScript; React / Vue / Angular.
      Hosting: S3 + CloudFront, Netlify, Vercel.

 2. BACKEND / API (the logic)
      Node.js (Express), Python (Flask, FastAPI, Django), Java (Spring).
      Receives requests, applies rules, talks to DB.
      Runs on: EC2, AWS Lambda (serverless), Elastic Beanstalk, ECS.

 3. DATABASE (stores data)
      SQL: PostgreSQL, MySQL (AWS RDS)
      NoSQL: MongoDB, DynamoDB
      Vector DB: Chroma, Pinecone (for RAG)
      Cache: Redis (fast temporary storage)

 4. AUTHENTICATION / AUTHORIZATION
      Login, passwords, roles. AWS Cognito, Auth0, Firebase Auth, JWT.

 5. FILE STORAGE
      Images, PDFs, uploads. AWS S3.

 6. WEB SERVER / REVERSE PROXY / LOAD BALANCER
      Nginx, Apache; AWS ALB to spread traffic across servers.

 7. DNS & DOMAIN & HTTPS
      Domain name (Route 53, GoDaddy), SSL certificate (ACM,
      Let's Encrypt) so the site is https://.

 8. VERSION CONTROL
      Git + GitHub/GitLab to store and share code.

 9. CI/CD (automation)
      GitHub Actions, Jenkins, AWS CodePipeline: on every push it
      runs tests, builds, and deploys automatically.

10. CONTAINERS (optional but common)
      Docker packages app + dependencies so it runs the same
      everywhere. Kubernetes/ECS to manage many containers.

11. MONITORING & LOGGING
      AWS CloudWatch, Grafana, Sentry: see errors, performance, alerts.

12. SECURITY
      Security groups/firewall, IAM roles (permissions), secrets
      manager, input validation, HTTPS.

13. THIRD-PARTY / EXTRA SERVICES (as needed)
      Email: SES, SendGrid.  Payments: Stripe, Razorpay.
      Queues/background jobs: SQS, Celery.  AI: Claude/OpenAI APIs.

9. PUTTING IT ALL TOGETHER (simple roadmap)
----------------------------------------------------------
 1. Plan functional features (login, upload docs, chat).
 2. Build locally (dev environment) with Git; push incrementally.
 3. Write unit tests, then integration tests (API + DB).
 4. Push -> CI runs tests automatically (GitHub Actions).
 5. Deploy to a test/staging environment (e.g. EC2 #1);
    run environment/smoke tests (/health).
 6. Run functional tests on the features.
 7. Deploy to production (EC2 #2 / Elastic Beanstalk / ECS),
    with a domain + HTTPS.
 8. Monitor logs, fix bugs, ship small updates repeatedly.

Final picture for a RAG chatbot web app:

   Browser (React)
        |  HTTPS
   Nginx on EC2  ->  FastAPI backend
                        |-> PostgreSQL (users, chat history)
                        |-> Vector DB (document embeddings)
                        |-> Embedding model
                        |-> LLM API (answer generation)
                        |-> S3 (uploaded files)
   GitHub -> GitHub Actions -> auto-deploy to EC2
   CloudWatch -> logs and alerts

Beginner advice: learn in this order -> Git -> HTML/CSS/JS ->
one backend language -> SQL -> deploy a tiny app on EC2 ->
add tests -> then try RAG with Chroma locally.
